# Internationalization (i18n)

Languages: **English (`en`)**, **Spanish (`es`)**, **Simplified Chinese (`zh-CN`)**, **Traditional Chinese (`zh-TW`)**. Library: [next-intl](https://next-intl.dev) in its "no URL prefix" mode — every language uses the same URLs.

## How the language is chosen

In order (first match wins), in `i18n/request.ts`:

1. **Cookie** `NEXT_LOCALE` (set by the header language switcher; 1 year).
2. **Browser language** (`Accept-Language`, honours q-values) via `negotiateLocale` in `lib/locale.ts`. Spanish → `es`; `zh-TW/HK/MO/Hant` → `zh-TW`; other Chinese → `zh-CN`; anything unsupported → `en`.
3. Default `en`.

It is remembered per user too: the switcher's server action `setLocale` (`app/actions/locale.ts`) writes the cookie **and** `profiles.locale`; after login `/auth/callback` copies the saved profile language into the cookie (so a new device gets the user's language), or saves the current language to the profile for first-time users.

## Merchant-written content

Merchants write in their own language (the **original**, stored in the normal columns) and can add **optional translations**. Stored as JSON in `translations` on `merchants` and `food_items`:

```json
{ "es": { "name": "Empanadillas", "description": "…" }, "zh-CN": { "name": "饺子" } }
```

- Editable on **Merchant → Profile** (name, description) and **Merchant → Foods → Edit** / the add form (`components/translation-fields.tsx`; form fields `tr_<locale>_<field>`, parsed by `parseTranslations`).
- Customers see the translation for their language if present, otherwise the original. `zh-CN` and `zh-TW` fall back to each other before the original. Logic: `localized()` in `lib/locale.ts`.
- Merchants themselves see the originals (their own admin screens, prep lists, reports).
- **Not translated:** pickup point names/addresses (proper nouns), holiday names (come from the Nager.Date API in English/local names), customer display names.

## Writing translatable code

- **Server components / actions:** `const t = await getTranslations("ns")`; **client components:** `const t = useTranslations("ns")`. Locale for formatting: `await getLocale()` (server) / `useLocale()` (client).
- Never hard-code user-visible text. Add the key to `messages/en.json` first; the keys are type-checked, so a typo fails `npm run typecheck`.
- Plurals use ICU: `"{count, plural, one {# order} other {# orders}}"` (Chinese messages can just use `{count} 筆`). Links inside text use rich tags: `"…<points>pickup point</points>…"` with `t.rich("key", { points: (c) => <Link>{c}</Link> })`.
- **Server actions return translated strings** (`FormState.error`), so the client just displays them. Zod schemas are built inside the action with `t(...)` messages.
- **Dates:** `formatDate(date, locale)`, `formatTime(time, locale)`. For an instant (cutoff) use `formatInstant(iso, locale, pickupPoint.timezone)` so it is shown in the pickup point's timezone with the zone name (Spanish/Chinese show `GMT-4` rather than `EDT` — that is Intl's per-locale naming). Use `todayIn(tz)` for "today at the pickup point"; never the server's date (servers run in UTC).
- **Database errors** are English (raised in SQL). `translateDbError(t, message)` maps known messages to `errors.*` keys; unknown ones show a generic message and are logged. New RPC error ⇒ add a pattern in `lib/db-errors.ts` **and** the key in all four catalogs (the test in `lib/__tests__/db-errors.test.ts` lists the mapped ones).

## Adding a string

1. Add to `messages/en.json` (right namespace), then the same key to `es`, `zh-CN`, `zh-TW`.
2. Use it in code. `npm test` includes `lib/__tests__/messages.test.ts`, which fails if any language is missing a key, has an empty message, or its `{placeholders}` / `<tags>` differ from English.

## Adding a language (e.g. French)

1. `lib/locale.ts`: add to `LOCALES`, `LOCALE_LABELS` (written in that language), `tagToLocale` (browser tag mapping) and `FALLBACKS` if it has a sibling.
2. Create `messages/fr.json` (copy `en.json`, translate).
3. New migration: widen the `profiles.locale` check constraint (`check (locale in ('en','es','zh-CN','zh-TW','fr'))`) — the original constraint is in `20261004000000_i18n.sql`; `ALTER TABLE … DROP CONSTRAINT … ADD CONSTRAINT`.
4. Add cases to `lib/__tests__/locale.test.ts`; run `npm test`.
5. Merchants can immediately add `fr` translations (the form iterates `LOCALES`).

## Translation quality

The Spanish and Chinese catalogs were drafted by an AI model and have **not been reviewed by native speakers**. Have someone review them — especially wording customers rely on (cutoff, pickup, QR) and anything you later add for legal text (privacy/terms) or allergens.

## Known gaps / ideas

- `app/manifest.ts` (PWA name/description) is English only.
- Pickup point names/addresses can't be translated; holiday names are not localized.
- No auto-translation of merchant text (could add an optional "translate with AI" button, mind allergy-related accuracy).
- No locale in URLs (shared links don't carry a language); switch to locale-prefixed routes only if SEO per language matters.
- Right-to-left languages would need `dir` handling and layout review.
- Email/push notifications (planned) must render in the recipient's saved `profiles.locale`.
